================================================================
전체 흐름: Vue → Spring → Redis → FastAPI → Redis → Spring → Vue
================================================================

[ Step 1 ]  파일 선택 시
----------------------------------------------------------------
① UUID 발급 요청
   - Spring이 UUID(taskId)를 발급해서 반환
   - Vue에 저장

② SSE 구독 요청  (taskId 전달)
   - Spring이 해당 taskId로 SSE 연결을 생성하고 등록
   - Vue는 연결 확인 후 작업 완료 이벤트를 대기


[ Step 2 ]  생성하기 버튼 클릭 시
----------------------------------------------------------------
PDF파일 + taskId를 Spring으로 전송

Spring 처리:
  1. 파일을 서버에 저장
  2. taskId / 저장 경로 / 원본 파일명을 Redis Stream(요청용)에 등록


[ Step 3 ]  FastAPI
----------------------------------------------------------------
- Redis Stream(요청용)을 상시 대기
- 메시지 수신 시 처리 시작

  처리:
    PDF 파싱 → 데이터 추출 → XLSX 파일 생성

- 완료 후 taskId / 결과 파일 경로를 Redis Stream(결과용)에 등록


[ Step 4 ]  Spring 결과 수신
----------------------------------------------------------------
- 앱 시작 시 Redis Stream(결과용) 구독 시작
- 메시지 수신 시
  → taskId로 SSE 연결 조회
  → 해당 Vue에 작업 완료 + 파일명 전달


[ Step 5 ]  Vue 다운로드
----------------------------------------------------------------
- 작업 완료 이벤트 수신
  → taskId를 store에 저장
  → SSE 연결 종료

- store 변경을 watch가 감지
  → taskId로 파일 다운로드 요청
  → Spring이 XLSX 파일을 Blob으로 반환
  → 자동 다운로드 실행 후 메모리 해제


================================================================
Redis Stream 역할
================================================================
  Stream (요청용) :  Spring  →  FastAPI   작업 요청
  Stream (결과용) :  FastAPI →  Spring    작업 결과 전달
================================================================

- Redis Stream 선택 - 단순 Pub/Sub 대신 Stream을 쓴 게 맞음. Pub/Sub은 구독자가 없을 때 메시지가 그냥 사라지는데,
                    Stream은 저장이 되기 때문에 FastAPI가 조금 늦게 떠도
  안전
  - Spring ↔ FastAPI 분리 - PDF/XLSX 처리처럼 무거운 작업을 FastAPI로 빼고 Redis로 연결한 구조는 실제 현업에서도 쓰는 패턴
    Spring이 작업 중에 블로킹되지 않아서 굿

  - SSE 선택 - 서버→클라이언트 단방향 알림이라 WebSocket보다 SSE가 훨씬 적합합 오버엔지니어링 안 한 거
  - taskId로 전체 흐름 추적 - UUID 하나로 Vue, Spring, FastAPI가 같은 작업을 식별하는 구조가 깔끔

  규모가 커지면 생각해볼 점 (지금 당장은 아님)
  - 현재 FastAPI가 재시작되면 처리 중이던 메시지를 유실 나중에 Consumer Group을 쓰면 해결
